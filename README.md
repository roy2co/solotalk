# עמדת סולו טוק 🎬💛

אפליקציית web (PWA) לעמדת ברכות וידאו לאירועים. אורח בוחר את רמת הקשר שלו ואת עומק
השאלות, מקבל ספירה לאחורה, והמצלמה הקדמית מקליטה אותו כשהשאלה **נצרבת בתוך הוידאו**.
ההקלטות נשמרות מקומית על המכשיר (IndexedDB) ומורדות ממסך הניהול.

## הפעלה מקומית

```bash
npm install
npm run dev
```

נפתח ב-`http://localhost:5173`. במחשב עם מצלמה אפשר לצלם ולראות את הזרימה המלאה
(כולל צריבת השאלה לתוך הקובץ). על localhost הדפדפן מאשר מצלמה בלי HTTPS.

## בנייה לפרודקשן

```bash
npm run build      # תיקיית dist/
npm run preview    # תצוגה מקדימה של הבנייה
```

## הרצה על האייפד

צילום מהמצלמה בדפדפן דורש **HTTPS** (מחוץ ל-localhost). לכן:

1. פורסים את `dist/` לאירוח סטטי עם HTTPS (Netlify / Vercel / GitHub Pages — חינם).
2. פותחים את הכתובת **בספארי** באייפד.
3. "שיתוף" → "הוסף למסך הבית" — נפתח במסך מלא כמו אפליקציה.
4. מאשרים גישה למצלמה ולמיקרופון בפעם הראשונה.
5. לנעילת העמדה: הגדרות → נגישות → **גישה מודרכת** (Guided Access), ואז לחיצה
   משולשת על כפתור הצד בתוך האפליקציה כדי להפעיל.

### ⚠️ חובה ספארי — כרום לא יעבוד

ב-iOS **רק** "הוסף למסך הבית" מספארי יוצר אפליקציה עצמאית. כרום (וכל דפדפן אחר
באייפון/אייפד) יוצר סימנייה רגילה שנפתחת בתוך הדפדפן — עם סרגל כתובת ובלי מסך מלא,
כי ההצהרות `apple-mobile-web-app-capable` ו-`display: fullscreen` פשוט לא נקראות.

אם הותקן בטעות מכרום: למחוק את הקיצור מהמסך ולהתקין מחדש מספארי.

### מה מסיר מה — נבדק בפועל

| מה מפריע | האם ניתן להסיר |
|---|---|
| סרגל הכתובת של הדפדפן | ✅ התקנה מספארי ("הוסף למסך הבית") |
| שורת הסטטוס של iOS (שעון, Wi-Fi, סוללה) | ❌ **נשארת.** ראו למטה |

**שורת הסטטוס נשארת, ואין דרך להסיר אותה באפליקציה.**

- **קוד (HTML/CSS/JS)** — בלתי אפשרי. iOS לא נותן לדף אינטרנט שליטה על שורת הסטטוס.
- **מצב standalone** — מסיר את ממשק הדפדפן בלבד, לא את שורת הסטטוס.
- **גישה מודרכת** — נועלת את המכשיר לאפליקציה אחת. **נבדק על אייפד: היא לא מסתירה
  את שורת הסטטוס.** (בעבר זו הייתה ההתנהגות באייפון; באייפדוס העדכני — לא.)
- **הדרך היחידה שכן עובדת:** להעביר את האייפד ל-**Single App Mode** דרך
  Apple Configurator. דורש Mac, כבל, ו"פיקוח" (supervision) על המכשיר — תהליך
  שמאפס אותו. זו הדרך של קיוסקים מסחריים.

מה שהקוד באפליקציה כן עושה: **מתאים את עצמו** לשורה (`env(safe-area-inset-top)`),
כדי שהכפתורים העליונים לא ייחבאו מתחת לשעון ולסוללה. זה בדיוק מה שהופך את השורה
לנסבלת — היא יושבת מעל הרקע הכהה של האפליקציה ולא מסתירה כלום.

### נעילת העמדה (גישה מודרכת)

לא מסתירה את שורת הסטטוס, אבל **מונעת מאורחים לצאת מהאפליקציה** — וזה מה שבאמת
נחוץ בעמדה באירוע.

הפעלה חד-פעמית:
1. הגדרות → נגישות → **גישה מודרכת** → להפעיל.
2. באותו מסך: **הגדרות קוד** → לקבוע קוד (זה מה שמאפשר לצאת בסוף הערב).

בכל אירוע:
3. לפתוח את אפליקציית סולו טוק מהמסך הבית.
4. **לחיצה משולשת מהירה על כפתור הצד** (או כפתור הבית בדגמים ישנים).
5. "התחל" בפינה הימנית-העליונה.

ליציאה בסוף הערב: לחיצה משולשת שוב + הקוד שקבעת.

> טיפ: בגישה מודרכת אפשר גם לנעול את **סיבוב המסך** — כדאי, כי העמדה עובדת לאורך.

## מסך ניהול (למפעיל)

כניסה: כפתור **⚙ בפינה השמאלית-העליונה** → מסך קוד → **קוד ברירת מחדל `1234`**
(ניתן לשינוי בדשבורד תחת "הגדרות מתקדמות"). לחיצה ארוכה באותה פינה עובדת גם היא.

| מה | קוד | ברירת מחדל |
|---|---|---|
| דשבורד ניהול | `adminPin` | `1234` |
| ארכיון אירועים | `eventsPin` | `0000` |

במסך הניהול אפשר:

- **לפתוח ולסגור אירוע** (שמות + תאריך) — עד שמתחילים אירוע, מסך הפתיחה סגור לאורחים.
- לראות **סטטוס גיבוי לענן** — כמה סרטונים עלו מתוך כמה.
- לערוך את שם האירוע, טקסט הפתיחה, תמונת הזוג, הלוגו וזמן האיפוס האוטומטי.
- לערוך את מאגר השאלות ולתייג כל שאלה לסוגי הקרבה שמתאימים לה (או להעלות CSV).
  ליד כל שאלה מוצג כמה פעמים אורחים **דילגו** עליה — סימן ששווה לנסח מחדש או להסיר.
- לצפות בהקלטות שנאספו, להוריד אחת-אחת או "הורדת הכל", ולמחוק.
- **☁️ צפייה** ליד כל הקלטה — קישור ישיר לקובץ בענן. נטען מיד, בניגוד למציג של
  קונסולת Firebase שמוריד את כל הקובץ לפני שהוא מציג אותו.
- **📋 העתק את כל הקישורים** — כל קישורי הענן של האירוע ללוח, בבת אחת.

## איך מוסרים את הסרטונים לזוג

**Firebase הוא שכבת הגיבוי, לא ערוץ המסירה.** אל תשלחו לזוג קישורי Firebase:

- **מסלול Spark (חינם): תקרת הורדה 1 ג"ב ליום.** אירוע שלם שוקל יותר מזה, ולכן
  ההורדות ייחסמו באמצע והזוג יחשוב שמשהו שבור.
- **מסלול Blaze: ~$0.12 לכל ג"ב יוצא.** ככל שהמשפחה תשתף ותוריד — אתם משלמים יותר.
- **אין "קישור לתיקייה" ב-Firebase Storage** — כל קובץ הוא כתובת נפרדת.

### הצינור הנכון

| שלב | מתי | מה |
|---|---|---|
| 1. גיבוי | בזמן האירוע | אייפד → Firebase, אוטומטי |
| 2. משיכה | בסוף הערב | Firebase → מחשב, פקודה אחת |
| 3. מסירה | למחרת | תיקיית Drive משותפת → **קישור אחד** לזוג |

**שלב 2** דורש Google Cloud SDK (התקנה חד-פעמית):

```bash
gcloud storage cp -r "gs://solotalk-df5d6.firebasestorage.app/recordings/<שם-תיקיית-האירוע>" ~/Downloads/
```

מוריד את כל סרטוני האירוע במקביל. עם **אפליקציית Drive למק** אפשר להוריד ישירות
לתוך תיקייה מסונכרנת, ואז שלב 3 הוא לחיצה ימנית → שיתוף.

### הייצוא מסונן לאירוע הפעיל

`📤 ייצוא` ו-`הורדת …` אורזים **רק את הסרטונים של האירוע הפעיל**, לא את כל מה
שנשאר במכשיר. הכפתור מציג את המספר מראש (למשל `📤 ייצוא 12 סרטוני האירוע`).

זה מה שהופך את **החזרה לאירוע** לשימושית: חוזרים לאירוע ישן, לוחצים ייצוא,
ומקבלים ZIP שמכיל בדיוק את הסרטונים שלו — גיבוי נקי, בלי ערבוב עם אירועים אחרים.

הסינון מכוון ל**אירוע הפעיל** ולא למה שמוצג ברשימה, כדי שהגיבוי יהיה צפוי ולא
ישתנה לפי מתג "הצג אירועים קודמים" שנשאר פתוח. **בלי אירוע פעיל** אין למה לסנן,
ואז נארז כל מה שבמכשיר.

> שם הארכיון הוא `soloTalk_<תאריך>_<שעה>.zip`. שם אירוע בעברית נמחק בסינון
> ה-ASCII, ולכן החותמת (עד רמת דקה) היא מה שמבדיל בין ארכיונים.

### ייצוא כארכיון ZIP אחד

`📤 ייצוא הכל` ו-`הורדת הכל` אורזים את כל ההקלטות ל**ארכיון ZIP** במקום להוריד
קובץ-קובץ. קודם לכן 25 הקלטות = 25 דיאלוגי הורדה נפרדים ב-iOS, ושיתוף של 25
קבצים בבת אחת נכשל בתוסף של Drive. **פריט אחד עובד.**

- **פיצול אוטומטי** מעל 500 מ"ב לארכיון (`ZIP_PART_MAX_BYTES` ב-`Admin.tsx`):
  אירוע של ~1.5 ג"ב יוצא כ-4 חלקים ממוספרים. עדיף כמה פריטים מפריט ענק אחד
  שעלול להפיל את תוסף השיתוף.
- **בלי דחיסה (שיטת STORE)** — הווידאו כבר דחוס, DEFLATE היה מבזבז זמן וחוסך ~0%.
- **בלי ספרייה חיצונית** — `src/lib/zip.ts`, כ-150 שורות. הארכיון נבנה כ-Blob
  שמצביע על ה-Blobs המקוריים, כך שאירוע שלם נארז **בלי להיטען לזיכרון**.
- מעל 4 ג"ב נזרקת שגיאה מפורשת (ZIP64 אינו נתמך) במקום ארכיון פגום בשקט.

**למה לא לסמוך על חלונית השיתוף:** תוסף Google Drive נכשל בפועל גם על קובץ בודד
(«חלק מהפריטים לא הועלו»). ה-ZIP משפר את הסיכוי משמעותית, אבל הצינור דרך המחשב
נשאר הדרך האמינה לסוף אירוע.

**למה קונסולת Firebase לא מספיקה:** כפתור ה-Download בה **מושבת כשמסמנים תיקיות**.
היא יודעת להוריד קובץ בודד בלבד.

## מצלמה והרשאות

### אין אישור קבוע לדף אינטרנט
**זו לא מגבלה של האפליקציה — אין שום API שמעניק הרשאת מצלמה קבועה.** ההרשאה
חיה במערכת ההפעלה, ואי אפשר להשפיע עליה מהקוד.

| דרך | מה משיגים | המחיר |
|---|---|---|
| **בדיקת מצלמה בדשבורד** | אישור **פעם אחת בתחילת הערב** — אף אורח לא רואה חלונית | אפס |
| הרשאה קבועה לאתר בספארי | נשמרת לאתר | חייב לרוץ **בספארי**, לא מהמסך הבית |
| עטיפה כאפליקציה נייטיב | אישור קבוע אמיתי | חשבון מפתח Apple, Xcode, הפצה |

**הנוהל לכל ערב:** דשבורד → **`🎥 בדוק מצלמה`**. ההרשאה מחזיקה לאורך טעינת הדף,
ולכן לחיצה אחת מכסה את כל האורחים.

### מה אומרת כל שגיאה
הודעת השגיאה נגזרת מ-`err.name` ולא מנוסחת אחידה — כי הכשלים שונים לגמרי:

| מה מוצג | מה קרה | מה עושים |
|---|---|---|
| «הגישה למצלמה נחסמה» | הרשאה נדחתה | «נסה שוב»; אם החלונית לא קופצת → הגדרות |
| «המצלמה תפוסה כרגע» | **iOS לקח את המצלמה** (למשל אחרי רקע) או אפליקציה אחרת | «נסה שוב» — בדרך כלל פותר מיד |
| «לא נמצאה מצלמה» | אין מצלמה | אין ניסיון חוזר |

**כפתור «🎥 נסה שוב»** קורא שוב ל-`getUserMedia` **מתוך לחיצה**, וזה מה שמקפיץ
מחדש את חלונית ההרשאה של iOS. הוא מתאושש בלי לרענן את הדף.

**preflight:** לחיצה על «התחל» בודקת את המצלמה **לפני** שהאורח עובר שלושה מסכים.
הגישה משוחררת מיד כדי לא לשרוף סוללה ולא להדליק את מחוון הפרטיות לשווא.

## כיוון העמדה — לאורך או לרוחב

נקבע לפי **מיקום המצלמה במכשיר**, לא לפי טעם. המצלמה צריכה להיות מעל המסך כדי
שהאורח יסתכל אליה בזמן שהוא קורא את השאלה:

| מכשיר | מיקום המצלמה | הכיוון הנכון |
|---|---|---|
| iPad Air M1 | בצלע הקצרה | **לאורך** |
| אייפדים חדשים / 13״ | בצלע הארוכה | **לרוחב** |

נבחר בדשבורד תחת **הגדרות מתקדמות → כיוון העמדה** (`auto` / לאורך / לרוחב).

**מה קורה בפועל:**
- בקשת המצלמה מתאימה את עצמה לכיוון המסך. מצלמה בכיוון הלא נכון נחתכת
  ב-`drawLoop` ומאבדת פיקסלים אמיתיים — ההתאמה חשובה לאיכות, לא רק לפריסה.
- הכיתוב הצרוב נגזר מהצלע ה**קצרה**, כדי שייראה זהה בשני הכיוונים. בגזירה
  מהרוחב, לרוחב הוא היה יוצא 96px במקום 54px — פי 2.3 ביחס לגובה הפריים.
- אם המכשיר לא בכיוון שנבחר, מוצגת בקשה **"סובבו את המכשיר"**. הגלגל של הניהול
  נשאר נגיש מעליה.

**iOS לא מאפשר לכפות סיבוב מקוד** — `screen.orientation.lock()` אינו נתמך
בספארי. הנעילה בפועל נעשית דרך נעילת הסיבוב של iOS או גישה מודרכת. שדה
`orientation` ב-manifest הוגדר ל-`any` כדי שהמכשיר יוכל להסתובב בכלל.

## חזרה לאירוע שהסתיים

סיום אירוע **לא מוחק אותו** — הוא נשמר, ואפשר לחזור אליו בכל עת.

**איך:** בתחתית דשבורד הניהול → **`🗂 ארכיון אירועים במכשיר`** → קוד
**`0000`** → רשימת כל האירועים עם שמות ותאריך → **`↩ חזור לאירוע`**.

הקוד נפרד מקוד הניהול (`1234`) בכוונה, כדי שאפשר יהיה לתת לעובד גישה לדשבורד
בלי גישה לארכיון.

**חזרה משחזרת את אותו `eventId`** — ולכן הקלטות חדשות נכנסות ל**אותה תיקיית
ענן** ומצטרפות לקיימות. זה בדיוק מה שרוצים כשחוזרים לאירוע אחרי כמה שבועות.

**כשיש אירוע פעיל** הוא מוצג בראש הרשימה מסומן `● פעיל עכשיו`, וכפתורי החזרה
של השאר מושבתים — כדי שאף אחד לא יסיים בטעות אירוע חי באמצע ערב. יש לסיים את
הפעיל תחילה.

### מחיקת אירוע מהמכשיר

לכל אירוע בארכיון יש **`🗑 מחק`**, שמסיר אותו **וגם את ההקלטות המקומיות שלו**.

**למה גם ההקלטות:** הרשימה נגזרת גם מ-`meta.eventId` של ההקלטות, ולכן מחיקת
הערך בלבד הייתה מחזירה את האירוע מיד. מעבר לכך — הערך עצמו הוא ארבעה שדות טקסט
(עשרות בתים); **מה שתופס מקום אמיתי הוא ההקלטות.**

לפני המחיקה מוצג אישור שמפרט בדיוק מה קורה: כמה הקלטות יימחקו, ו—
- ✓ ירוק כשהכל מגובה: **הגיבוי בענן לא נפגע.**
- ⚠️ אדום כשלא: «N סרטונים עדיין לא עלו לענן — מחיקה תאבד אותם לצמיתות».

**Firebase לעולם לא נמחק מכאן.** הענן הוא שכבת הגיבוי, ומחיקה מקומית לא אמורה
להשמיד אותה. למחיקה מהענן יש להשתמש בקונסולת Firebase.

**אין השפעה להשאיר אירועים בארכיון** — הם לא משפיעים על ההקלטות, על הענן או על
הביצועים. המחיקה היא לסדר בלבד.

הרשימה נבנית מההיסטוריה השמורה **ממוזגת** עם אירועים שנגזרים מ-`meta.eventId`
של ההקלטות שעדיין במכשיר — כך שאירוע ניתן לשחזור גם אם הקונפיג אבד.

> ⚠️ **עובד על אותו מכשיר בלבד.** הקונפיג נשמר ב-IndexedDB מקומי ואינו מסונכרן.
> אירוע שנפתח באייפד אחד לא יופיע ברשימה של אייפד אחר, וגם הקוד לא ימצא אותו.
> סנכרון בין מכשירים הוא מיילסטון עתידי ("ניהול מרכזי").

## איכות הווידאו

| פרמטר | ערך | איפה |
|---|---|---|
| בקשת מצלמה | 1080×1920 (פורטרט) | `recorder.ts` `openCamera` |
| קנבס (לאורך) | 1080×1440 | `CANVAS_LONG_SIDE` |
| תקרת קצב | 4.5 Mbps | `VIDEO_BITS_PER_SECOND` |
| תקרת זמן הקלטה | 4 דקות | `MAX_RECORDING_MS` ב-`Recording.tsx` |

**למה זה מה שקובע את האיכות:** הקנבס הוא פורטרט ו-`drawLoop` חותך את המצלמה כדי
להתאים. מ-720p לרוחב נותרו רק 540×720 פיקסלים אמיתיים שנמתחו על כל הפריים.
לכן מבקשים 1080p **בפורטרט**:

| מה המצלמה נותנת | פיקסלים אמיתיים בפריים |
|---|---|
| 1280×720 לרוחב (הישן) | 540×720 |
| 1920×1080 לרוחב | 810×1080 |
| **1080×1920 פורטרט** | **1080×1440** — בדיוק גודל הקנבס, בלי מתיחה |

iOS לא תמיד מכבד בקשת פורטרט, ולכן `ideal` (ולא `exact`) — ובדשבורד, תחת
**"איכות ההקלטה במכשיר הזה"**, מוצג מה המצלמה **באמת** נתנה בהקלטה האחרונה.
זו הדרך היחידה לדעת מה קורה על האייפד בפועל.

**4.5 Mbps היא תקרה, לא קצב קבוע.** H.264 הוא VBR ומוציא רק מה שהתוכן דורש —
בבדיקה על תוכן בסגנון "ראש מדבר" הוא השתמש ב-~2 Mbps. סרטון של 2.5 דקות צפוי
לשקול 40–80 מ"ב בהתאם לכמות התנועה והפירוט.

**תקרת הזמן היא הגנה על הזיכרון:** ההקלטה נצברת כולה בזיכרון עד לשמירה. מעבר
ל-~4 דקות טאב ספארי באייפד עלול ליפול, ואז ההקלטה אובדת. האורח רואה ספירה
לאחורה ב-30 השניות האחרונות וההקלטה נסגרת מסודר.

## מבנה הקוד

```
src/
  types.ts            טיפוסים משותפים
  lib/
    config.ts         קונפיג ב-localStorage + ייבוא/ייצוא
    questions.ts       מאגר שאלות ברירת מחדל
    recorder.ts        ★ הליבה: canvas + MediaRecorder עם צריבת שאלה
    storage.ts         ממשק אחסון + מימוש IndexedDB (מוכן להרחבה לענן)
  screens/            Welcome · Relationship · Depth · Countdown · Recording · ThankYou · Admin
  App.tsx             ניתוב בין המסכים + state של הסשן
```
